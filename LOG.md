# Decision Log

Non-obvious product/architecture decisions and the reasoning behind them, in the order they were made. Newest entries at the top. The code shows _what_; this shows _why_ — append here whenever a decision wouldn't be obvious from reading the diff alone.

---

## 2026-07-05

- **"People" now means everyone in the publication graph, not just pre-vetted lab members.** `src/lib/ingestion/people.ts`'s `resolveOrCreateTeamMember` deliberately reverses this file's own 2026-07-03 "Team is never written by importers" position: on a safe-person-match miss, Publications ingestion now creates a real `team` record for every co-author instead of dropping them into `Publications.authors[].customAuthor` as a free-text holding pen. Reason: the holding-pen version pushed the identity/data-entry work back onto the operator, which is exactly the toil the ingestion product was supposed to eliminate. The safety split is **unchanged**: ORCID/DBLP-exact and exact-name-only remain the only auto-link tiers; fuzzy people-name matches are still never auto-applied to an existing Team row, only surfaced as `report.suggestDedupe` / `review-items` merge suggestions for a human to confirm later. The crucial public-site safety invariant is now centralized in one unconditional `data` object reused by both the `upsertByKey(...)` path and the plain `payload.create(...)` fallback in `resolveOrCreateTeamMember`: every importer-created person gets `source: 'import'` and `displayInWebsite: false`, making "is in the publication graph" and "is shown on the website" two intentionally separate decisions.
- **`import-runs` and `review-items` are now first-class persistence, even for dry-runs, because they serve different lifecycles.** `src/collections/ImportRuns/index.ts` is immutable run history (`params`, staged `candidates`, `progress`, final `reportSummary`); `src/collections/ReviewItems/index.ts` is a mutable work queue (`status`, `resolution`) that operators work down over time. The engine shape in `src/lib/ingestion/staging.ts` and `src/lib/ingestion/run-persistence.ts` is now explicitly two-phase: staging fetches/parses only (`stageOrcidCandidates`, `stageBibtexCandidates`, `stageCitationCandidates`) and does **no** Crossref/OpenAlex hydration or DB writes; hydration/persistence happens afterward, with `persistRunProgress` and `finalizeRun` writing the bookkeeping regardless of `dryRun`. That `dryRun` gate is intentionally narrower: only the real content collections (`publications`, `team`, `venues`, `organizations`) no-op their writes, while runs/history/review-queue still persist so CLI dry-runs and the future dashboard both have an auditable record of what happened and what still needs human review.
- **Live verification against Nova Ahmed's career-wide ORCID confirmed the write boundaries and the new bookkeeping model on real data.** Running `pnpm payload run scripts/ingestion/import-orcid.ts 0000-0002-7715-1742 dry-run` completed successfully on a 122-work ORCID record. Final dry-run report: `organizations` 94 `skipped-dry-run`, `team` 261 `skipped-dry-run`, `venues` 23 `skipped-dry-run`, `publications` 108 `skipped-dry-run` plus 9 `skipped-existing`; 73 unmatched relations and 4 merge suggestions. Mongo verification against `mongodb://127.0.0.1/payblocks` confirmed the dry-run did **not** write real content rows: `team` stayed 0, `publications` 58, `organizations` 38, and `venues` 47 before/after; only bookkeeping changed (`import-runs` 2 -> 3, `review-items` 77 -> 154). The newest CLI run (`import-runs` id `6a498e3f523f8279571ed55f`) finished `completed` with `params.orcidId = '0000-0002-7715-1742'`, `params.dryRun = true`, `progress.total = 122`, `processed = 122`, `created = 108`, `skippedExisting = 9`, `failed = 5`, and a populated `reportSummary`. Its linked `review-items` queue contains 77 rows (`run` relationship to that id): 68 `unmatched-venue`, 5 `no-doi-work`, and 4 `person-merge-suggestion`, which is exactly the behavior the dashboard needs from a dry-run over a career-wide, non-lab-scoped ORCID corpus.

## 2026-07-03 (even later)

- **DBLP added as a third structural author-matching tier**, alongside ORCID and exact-name in `matchPersonToTeam`/`dedupeCustomAuthor` (`src/lib/ingestion/people.ts`). Unlike ORCID (sparse in practice — see this doc's earlier entry) DBLP publication records embed already-disambiguated author `pid`s per paper, so it's structural third-party evidence, not a name-similarity guess — safe to rank alongside ORCID, above exact-name, still nowhere near the banned fuzzy tier for people. `Team.dblp_pid` is manual-entry only (mirrors `orcid`/`openalex_id` exactly) — never auto-searched-and-assigned, which would reintroduce the homonym risk this design avoids.
- **Resolution is title+year search (`dblp.org/search/publ/api?format=json`), not a DOI endpoint** — DBLP has no confirmed direct DOI lookup. Verified live against a real CHI 2026 DOI before writing `src/lib/ingestion/dblp.ts`: the search JSON embeds `info.authors.author[].{@pid,text}` inline, so no XML-parsing fallback or new dependency was needed after all (the plan's contingency for this went unused). One real quirk confirmed live: DBLP's XML-to-JSON conversion collapses a single-item list (`hits.hit`, `authors.author`) to a bare object instead of a one-element array — handled with a small `asArray()` normalizer, same defensive-shape pattern as `normalizeIssn` from the prior entry.
- **DBLP enrichment is additive and silent-on-miss, not a hard requirement.** DBLP only covers ACM/IEEE/CS venues (not JMIR-type medical-informatics venues also in DIAL's corpus), so `hydratePublicationFromDoi` never calls `flagUnmatched` when DBLP has no record — only Crossref+OpenAlex both missing is treated as a hard failure, same as before this change.
- **Author-list alignment between DBLP and Crossref/OpenAlex uses name-similarity matching (`attachDblpPids`), not array position** — unlike `mergeAuthors`' Crossref/OpenAlex merge (which reuses position since both APIs preserve submission order), DBLP's own author count/formatting can differ slightly (e.g. accented names, middle-initial handling), confirmed live: DBLP rendered "Dragan Ahmetović" without the accent, but dice-coefficient similarity against the normalized name still matched all 4 authors on a real CHI 2026 paper correctly on first live test.

## 2026-07-03 (later)

- **Built the general Publications ingestion pipeline** (`src/lib/ingestion/publications.ts` + `scripts/ingestion/import-{orcid,citations,bibtex}.ts`), replacing the fixture-only `hydrate-dial.ts` Publications path with a live one. One shared core (`hydratePublicationFromDoi`/`hydratePublicationFromFields`) that all three front doors funnel into — matches the "one engine, multiple front doors" framing in @docs/product/ROADMAP.md.
- **Author disambiguation now exists, split into two deliberately different safety tiers** (`src/lib/ingestion/people.ts`): `matchPersonToTeam` (ORCID-exact or exact-full-name-only, safe to auto-link to a real Team record) vs. `dedupeCustomAuthor` (ORCID-exact auto-reuses a prior `customAuthor` identity across papers; fuzzy name match is surfaced as a report suggestion, never auto-applied). Reusing `resolveByName`'s fuzzy tier for either was rejected — that tier is explicitly org/venue-only per this doc's own prior entry on homonym risk. Verified live against a real ORCID (72 works): the fuzzy-suggestion tier correctly fired for repeat co-authors across different papers within one run, and never for the ORCID-exact tier only when both papers actually gave an ORCID (most didn't — Crossref's per-author ORCID coverage is sparse in practice, confirming this doc's earlier finding about Crossref/OpenAlex ORCID coverage).
- **Organizations and Venues both got a ROR/ISSN-or-OpenAlex-Source-ID auto-create gate** — auto-create only when OpenAlex supplies a safe external identifier and nothing existing matches it; a bare name never triggers auto-creation, only a flagged review item. This is stricter than this doc's 2026-07-02 "Organizations — partner institutions: Yes" framing implied (no gate was specified there) and deliberately extends the same posture to Venues, which the ROADMAP's collection table had marked "Yes, once extended" with no caveat at all. Confirmed live: real ORCID-driven runs produced ~35 flagged (no-identifier) venues per run vs. a handful of ROR-identified auto-creatable orgs — ACM/IEEE conference proceedings routinely lack OpenAlex Source IDs/ISSNs, matching this doc's 2026-07-03 note that "ACM/IEEE proceedings don't carry ISSNs."
- **Re-import never overwrites an existing Publication** — both `hydratePublicationFromDoi` and `hydratePublicationFromFields` check for an existing record (by DOI / by title) before doing any work and skip entirely if found, rather than `upsertByKey`'s normal full-overwrite-on-match behavior. Deliberate deviation from `hydrate-dial.ts`'s one-time-bounded-corpus behavior, because these scripts are meant to be re-run repeatedly as a lab adds papers — a second run must not silently clobber a human's post-import edits in the admin. **Caught by testing, not by design review**: the first implementation only added this check to the DOI path; a live smoke-test re-run of a BibTeX-only (no-DOI) entry showed it still going through `upsertByKey`'s update-on-match branch. Fixed by adding the identical existence-check-first pattern to `hydratePublicationFromFields`.
- **`Grants.investigators[].customInvestigator` and `Awards.recipients[].customRecipient`** upgraded from bare `text` to the same `{name, orcid, affiliation}` group `Publications.authors[].customAuthor` got earlier this session — schema consistency so the same author-index (`buildCustomAuthorIndex`) can scan all three surfaces, even though Grants/Awards stay manual-entry with no ingestion writer of their own.
- **`@retorquere/bibtex-parser`'s published package has a types-path bug** — `package.json` declares `"types": "./dist/types/index.d.ts"` but that path doesn't exist in the actual npm tarball (only `dist/cjs`/`dist/esm`/`dist/data` ship). Added a local ambient declaration (`src/types/bibtex-parser.d.ts`) rather than assume the library's own docs/types were accurate — also caught by inspecting the real shipped code that `year` fields come back as a numeric-formatted **string** (`FieldAction.parseInt` returns a template-literal string, not a real `parseInt` result), not a number as its behavior might suggest; `import-bibtex.ts` parses it explicitly.
- **`Venues.issn` widened from a single `text` field to `hasMany`** (Codex review caught: persisting only `issn[0]` on venue auto-create would miss a later import's different print/electronic ISSN variant for the same venue and create a duplicate). `resolveVenue` now merges Crossref's and OpenAlex's ISSN arrays, matches on any overlap, and persists all of them; `warnDuplicateVenue.ts` updated for array-aware matching (`{issn: {in: [...]}}` instead of `{equals}`). **Caught a second bug via live testing against DIAL's actual seeded corpus** (not synthetic data): Payload does not migrate existing Mongo documents when a field's `hasMany` flag changes, so DIAL's real pre-existing `Journal of Medical Internet Research` venue record — written before this change — still stores `issn` as a bare string, not an array, and crashed `entry.issn?.some(...)`. Fixed by normalizing at the read boundary in `loadPublicationIndexes` (`normalizeIssn`: accepts either shape) rather than assuming all rows already match the current schema. This is the general lesson: a Payload field-shape change is not retroactive, and code reading older collections must tolerate the pre-change shape until/unless a real migration runs.

## 2026-07-03

- **`Publications.authors[].customAuthor` changed from a bare `text` field to a group (`name`, `orcid`, `affiliation`).** Reason: the Team-matching problem isn't really "match a name against Team" — it's that every unmatched co-author across every ingested paper already sits in this field, but a plain string gives the future matcher nothing safer than name-only comparison, which `resolveByName`'s design already flagged as homonym-risky for people. Storing `orcid` (from OpenAlex `authorships`, when present) and `affiliation` (relationship to Organizations, reusing the partner-org matching already built for `Team.affiliation`) turns this field into the identity registry itself — no new collection needed — and gives the AUT-133 matcher an exact-match tier (ORCID equality) before it has to fall back to fuzzy name/affiliation. **Not yet populated by anything**: no ingestion code today extracts author lists from Crossref/OpenAlex responses at all (`mapCrossrefToPublicationFields`/`mapOpenAlexToPublicationFields` only cover work-level fields), so this is schema groundwork ahead of the writer, not a working feature. Updated `formatAuthorsACM.ts` and `hydrate-dial.ts` for the new shape; regenerated `payload-types.ts`.
- **Roadmap's "which collections ingestion touches" table was conflating two different axes — split into write target vs. read/match target.** A collection can be consulted by the engine during a match step without ever being written to, and Team is exactly that case: nothing in the ingestion pipeline (now or in the planned AUT-131 scripts) ever creates or updates a Team record. Team is only ever _read_ — consulted when resolving `Publications.authors[]` to decide whether an author name links to an existing Team record (`teamMember`) or falls through to free-text `customAuthor`. The previous "Assisted, not automatic" language in the table was describing a feature that doesn't exist yet (surfacing `customAuthor` matches when a new Team record is created) as if it were current behavior. See @docs/product/ROADMAP.md's "Which collections ingestion actually touches" table.
- **Filed [AUT-133](https://linear.app/autana-systems/issue/AUT-133/team-promotion-flow-suggest-linking-customauthor-entries-to-new-team)** for the Team promotion flow (people-name matcher + "promote" admin action to convert matching `customAuthor` entries to `teamMember` relationships), blocked by AUT-131. Deliberately scoped separately from AUT-131 — it needs real `customAuthor` data from an actual ingestion run to build and test against, and reusing `resolveByName` directly for people (rather than orgs/venues) is risky given homonyms, so it needs its own matcher design.

## 2026-07-02

- **Track 1 (`hydrate-dial.ts` over hand-curated markdown) retired as DIAL's _Publications_ data source only — not deleted, and not fully superseded.** It already did its job schema-freezing against real data. Its `hydratePublications`/`hydrateVenues` logic is genuinely dead weight once the general pipeline exists (ORCID/citation-wall/DOI-paste replace it) and is the only part still inline in the script. `hydrateGrants`, `hydrateAwards`, `hydrateProjects`, and `hydrateTeam`'s manual-field handling (role mapping, bio-to-Lexical, affiliation resolution) solved a problem nothing else in the repo solves — Grants/Awards/Projects/Research Themes are permanently manual (no external API tracks them) — so they've been **extracted into `src/lib/ingestion/{grants,awards,projects,team}.ts`** as normalized-input functions decoupled from DIAL's markdown shape, giving the future LabKit manual-entry CLI/MCP/skill a real starting point instead of a script to reverse-engineer. `hydrate-dial.ts` now just maps its markdown fields into those normalized shapes and delegates. Verified byte-for-byte identical dry-run output (counts + 31 unmatched relations) before/after the extraction. `probe-doi.ts`'s fetch logic (`fetchCrossrefByDoi`, `fetchOpenAlexByDoi`, `searchCrossrefByTitle`) and coverage-report generation (`buildCoverageReport`) are similarly promoted into `src/lib/ingestion/fetch.ts` and `coverage.ts`; `probe-doi.ts` now accepts arbitrary DOI args instead of only reading DIAL's fixtures, making it a reusable onboarding diagnostic for future labs, not just a one-off. (One cleanup caught in review: the extraction had left a duplicate, dead copy of the coverage functions inline in `probe-doi.ts` that lint didn't flag — deleted.) See @docs/product/ROADMAP.md.
- **OpenAlex restricted to per-DOI enrichment only** (abstract reconstruction, open-access status, `authorships` → co-author institution). Never author-search/identity resolution. Reason: DIAL has no claimed OpenAlex author profiles, and OpenAlex's author disambiguation without one is an algorithmic guess. Confirmed by pulling Nova Ahmed's real ORCID record — her ORCID is populated entirely by Crossref/Scopus DOI-anchored auto-push (0 self-asserted entries), which is a materially more trustworthy author→work link than OpenAlex author search would be.
- **Ingestion ladder re-ranked**: ORCID pull and citation-wall paste are the priority front doors, not ORCID → DOI-paste → BibTeX → citation-wall → scrape as originally sequenced. Reasoning: no lab natively maintains a raw DOI list — it was never a realistic onboarding input, only an internal engine shape. Citation wall (a docx/PDF of citations grouped by year) is the actual median artifact most labs have, and its segmentation is cheaper than first assumed — docx paragraphs are already citation boundaries, so LLM segmentation is only needed for the unstructured-paste tail, not the common case.
- **Review step is required starting at rung 1 (ORCID), not deferred to citation-wall.** Confirmed against Nova Ahmed's real ORCID: 122 works spanning 2004-2026, career-wide rather than lab-scoped (pre-2014 systems/RFID work mixed with DIAL-era accessibility work). A raw "N works imported" from ORCID would be wrong. Review can start as a CLI dry-run report (extending `ImportReport`) rather than a full UI, since the operator is currently the concierge, not the PI.
- **Ingestible/manual collection boundary established**, backed by real coverage numbers from the 21-DOI DIAL probe (`docs/clients/dial/dial-data/_fixtures/coverage-report.json`): Publications and Venues are fully ingestible (Venues via `container-title`/ISSN, once the Crossref mapper is extended to pull them — not done yet). Organizations split: partner institutions are ingestible via OpenAlex `authorships`, but funders are not — confirmed dead on real data (Crossref `funder` 2/21, OpenAlex `grants` 0/21). Team is assisted (an ORCID/DOI-driven suggestion to link a `customAuthor` entry when a new Team record is created) but never automatic — membership is always a deliberate human act. Grants, Awards, Research Themes, and Projects have no external bibliographic source and stay fully manual; Projects is additionally an optional, lab-toggleable concept, not a universal one.
- **Content-ops split decided**: the ingestion engine handles external-API bulk pulls (Publications, Venues, partner Organizations); a future LabKit CLI / MCP server / Claude Code skill (shape undecided) handles human-authored bulk entry (Projects, Awards, Grants, Themes, Team-linking); the Payload admin dashboard is reserved for surgical single-record edits, not primary data entry for any of the above.
