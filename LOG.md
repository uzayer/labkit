# Decision Log

Non-obvious product/architecture decisions and the reasoning behind them, in the order they were made. Newest entries at the top. The code shows _what_; this shows _why_ — append here whenever a decision wouldn't be obvious from reading the diff alone.

---

## 2026-08-18

- **Draft-preview authorization no longer puts `NEXT_PRIVATE_DRAFT_SECRET` in the URL.** Payload's authenticated, HTTP-only session cookie is the request credential for `/next/preview`; the route authenticates that session before enabling draft mode, and the configured draft secret remains server-only as a feature gate. This avoids leaking a reusable secret through browser history or referrer headers while preserving the existing rule that preview is disabled unless the environment explicitly configures it.

- **DIAL's canonical name is “Design Inclusion and Access Lab,” and its workspace now separates kinds of truth.** `dial-test/` remains authoritative for implemented layout and interaction, current Payload collections/ingestion code define the production data contract, raw captures plus Lab confirmation establish facts, and `labs/dial/dial-data/` is deliberately retained as unverified but realistic working material. Structured scraped data is useful for prototype and import work without being treated as approved public copy. Conflicting prototype expansions of DIAL were normalized to the confirmed name.

- **The DIAL design archive was collapsed into an active delivery contract.** Nineteen overlapping root/page planning files became `identity.md`, `frontend.md`, and `design-principles.md`; the superseded `/events` spec and obsolete scratch notes were deleted with Git as their archive. The new frontend contract records prototype composition, production Payload mapping, launch gates, and open decisions separately so implementation drift does not silently erase product intent. Raw captures stay under `scraped-data/` with an explicit provenance policy.

- **Importer-owned and raw-source Markdown is excluded from oxfmt.** Some `dial-data` files contain YAML in Markdown bodies, where general Markdown formatting can change indentation and make `gray-matter` parsing fail; scraped captures should also remain verbatim evidence. `.oxfmtrc.json` now ignores both `labs/dial/dial-data/**` and `labs/dial/scraped-data/**` while ordinary DIAL planning Markdown remains formattable.

- **The future docs site has a reusable-content boundary.** `docs/` is plain Markdown for durable LabKit product, Operator, Lab Editor, and contributor knowledge; Fumadocs and MDX remain later work. DIAL source material and page-building notes moved to `labs/dial/`, while `dial-test/` remains the standalone prototype. Generic Payblocks setup, database, deployment, and email pages were deleted instead of maintained as LabKit documentation. The first stable onboarding procedure now lives at `docs/operator/onboard-a-lab.md` and must be appended to during each real import and review pass.

- **The public CMS catch-all renders dynamically rather than querying MongoDB during image builds.** A Docker image is built before Docker Compose starts its MongoDB service, while Next's default static rendering would run both `generateStaticParams` and the shared Header/Footer/ThemeConfig reads at build time. The catch-all is now explicitly dynamic, and Docker's builder skips static params so the standalone image contains no database credential or build-time database dependency. CMS pages resolve their current Payload data on request, which is also the correct behavior for content the Lab Editor changes after deployment.

- **Draft mode now observes Payload collection access instead of becoming an implicit superuser path.** Entering preview requires a configured draft secret and an authenticated Payload session, and page/post/project reads pass that authenticated user into the Local API with `overrideAccess: false`. A stale or forged draft cookie falls back to the public, published-only query; preview and content-read approvals/rejections are logged without secrets. Runtime validation rejects weak configured secrets in production while retaining the example's demo values for local development, and cron backup validation reuses the same policy. `NEXT_PRIVATE_DRAFT_SECRET` rotates every 90 days and is unique per environment. IP allowlisting and a separate preview re-authentication timer stay deployment-specific policies rather than default application behavior.

- **Package installs must be workspace-aware even though this is not a real monorepo.** `pnpm ii` and `reinstall` previously used `--ignore-workspace`, which also ignored `pnpm-workspace.yaml`'s reviewed `allowBuilds` policy. Modern pnpm consequently refused the legitimate lifecycle scripts for `@google/genai`, `esbuild`, `protobufjs`, and `sharp`, making the documented install command fail. Both wrappers now use `pnpm install`; the workspace still contains only `.` and continues to exist only for root dependency-resolution policy.

Session was a scoping/strategy grilling after ~6 weeks of no commits, resuming a project that had never shipped. Outcome: an MVP was defined and a large amount of speculative scope was cut. No code changed; `CONTEXT.md` and `docs/adr/0001-defer-cerif-alignment.md` were created.

- **The MVP is "DIAL's public website is live," and nothing else.** Scope, in order: (0) keep a runbook of every manual step while doing it; (1) port `dial-test/`'s routes into `src/app/(frontend)/` against the Payload Local API, DIAL-shaped; (2) first real non-dry-run ingestion of DIAL's data via ORCID + BibTeX; (3) hand-clean the review fallout in the Payload admin; (4) `admin.group` across collections so the admin reads as a deliberate v1 dashboard; (5) deploy, hand over, ask for the testimonial on launch day. Explicitly **out**: the dashboard port, CERIF, all compliance work, multi-lab/theming generalization, scrape-to-demo automation, OpenAlex weekly sync, AUT-133 promotion flow, and Semantic Scholar / arXiv / PubMed enrichment.
- **The bottleneck was misidentified: ingestion is the most finished part of this project and the frontend is the least.** The session opened with "what's the bare minimum I can ship for ingestion?" — the honest answer is _what already exists_, since `LOG.md` 2026-07-05 records a verified end-to-end run over a real 122-work ORCID producing 108 publications, 261 people, 94 orgs and 23 venues, with a working review queue. Meanwhile `dial-test/` is **not** "a template not yet wired to the schema" as `CLAUDE.md` described it: it is fully static, with **zero** `fetch` calls and zero `process.env` usage across ~20 routes, and its hardcoded publication arrays contain **fabricated** papers ("Jyoti", "Shathi") rather than DIAL's real corpus. It is a design prototype, not a frontend. Correspondingly `src/app/(frontend)/` has **no lab-facing routes at all** — 15 files, all infrastructure (catch-all Hero page, preview, OG, backup, early-access). Item 1 above is therefore ~90% of the MVP; items 2–5 are days.
- **The port is DIAL-shaped on purpose, and the named failure mode is refactoring toward generality mid-port.** dial-test's components expect flat view-models (`authors: string`, `venue: 'CHI'`, `citationText`, `themes: string[]`) while the schema has relationships and `customAuthor` groups, so every page needs a small mapping layer — tedious ~20 times, which is exactly the pressure that has historically triggered premature generalization here. The guardrail agreed: **hardcoding DIAL's nine research themes as routes is allowed**; if a themes-router starts getting written, stop. Lab #2 (MI Lab at NSU), not lab #1, is the product-defining moment — it is the first time the frontend and engine meet a lab that wasn't designed around. Everything should be sequenced to reach lab #2 fast, not to make lab #1 perfect. Versions are compatible for the port: labkit is Next 16.2.10 / React 19.2.7 / Tailwind v4, dial-test is Next 16.2.4 / React 19.2.4 / Tailwind v4, same shadcn setup; extra deps it brings are `three`, `@react-three/fiber`, `embla-carousel`, `motion`, `vaul`, `radix-ui`.
- **`Pages` cannot hold body content, and that is not to be fixed — the routes split by churn instead.** Verified: `Pages` has only `title`, hero, `meta`, `publishedAt`, `enableBreadcrumbs` — no layout/blocks field, since the page-builder system was removed. Rather than restore blocks, the rule is: **data-driven routes** (publications, people, projects, awards, research themes, news) get wired to Payload because they churn and are the entire value proposition; **prose routes** (about, contact, join-us, home copy) stay hardcoded in the component because a Lab edits them approximately never and the Operator can change them by hand in five minutes. This roughly halves item 1 and is a deliberate scoping of the CMS to what actually changes, not a compromise.
- **The bar for cleaning review fallout is "presentable," not "clean."** The dry run produced 77 review items on 122 works, 68 of them unmatched venues, which looks like a wall. But a free-text `venueLabel` renders identically on the site to a properly linked Venue record, so the rule for item 3 is to fix only what looks wrong on the _rendered page_ and timebox it to a day. Do not perfect the graph before launch.
- **Two things were missing from the MVP list and were added: media and the runbook.** Nothing in the ingestion pipeline produces images, and `labs/dial/dial-data/` is markdown — so team photos and project images are manual collection and upload, the classic last-day launch blocker. And `ROADMAP.md` already committed to a per-lab runbook; since lab #2 is the product-defining moment, the runbook is the bridge to it, free to write while doing and expensive to reconstruct after. Also flagged as a stakeholder decision with real lead time (DNS + NSU IT): does this replace DIAL's site at its current URL or launch on a subdomain? Settle it early, not at launch.
- **"Paste your ORCID, get your lab's website" only has to be true _in effect_, which cuts the entire dashboard port from the MVP.** The Operator runs the CLI; the Lab sees only the filled site. The claim stays honest — someone did paste their ORCID — and it is precisely `ROADMAP.md`'s scrape-to-demo motion, where a prospect receives a link to their own site already filled before first contact and never sees a terminal. Making it _literally_ true (a UI a Lab Editor drives) requires porting the import wizard and review queue with self-serve error handling — months, for a claim that is already sellable today.
- **Google Scholar is already a supported front door and needs no new code.** Google Scholar has **no API** and scraping it is ToS-risky and bot-detected, but every Scholar profile has a native **Export → BibTeX → "All my articles"** button, and `scripts/ingestion/import-bibtex.ts` already handles exactly that output shape (DOI → Crossref/OpenAlex; no DOI but a title → Crossref reverse-title lookup; neither → written from BibTeX fields alone, flagged for review). The two sources are good at different things and the split follows from that: **cold demos use ORCID** (the only one with a legitimate public API, so nothing is needed from the Lab), **warm onboarding uses Google Scholar BibTeX** (better researcher coverage, and two clicks is nothing once they've said yes). ORCID's data is materially cleaner — DOI-anchored, per this log's own 2026-07-02 finding that Nova Ahmed's 122-work record was populated _entirely_ by Crossref/Scopus auto-push with zero self-asserted entries — whereas Scholar profiles are auto-populated and noisy (preprint+published duplicates, occasional wrong-author papers, frequently no DOI).
- **"Nobody has modelled a lab's data" was false and the correction is load-bearing for the paper.** The domain is heavily modelled: **CERIF** (euroCRIS, ~200 institutional/national systems, EU-recommended, v1.6.1 with 2.0 mid-refactor), **VIVO** (open source and _actively maintained_ — repo last pushed 2026-08-13, latest tag vivo-1.16.0, a June 2026 PR wiring ORCID auth; what died was the VIVO-ISF **ontology working group**, whose W3C community group closed April 2023, which is what made it look abandoned), **DSpace-CRIS** (the one open-source CRIS that is also a repository), Haplo Research Manager, and the commercial trio Pure / Symplectic Elements / Converis — all three of which are proprietary relational schemas that nonetheless **implement CERIF** for interchange. The true statement is narrower and stronger: **every one of these is institution-scale, and no institutional office owns "the lab."** The library models the university's publications, the research office models its awards, HR owns people, and faculty maintain CVs in Word — the lab is below the granularity all of it operates at. That is the gap.
- **DSpace-CRIS is not a competitor because it is a different unit of adoption, and this was checked rather than assumed.** Per the official DSpace 9.x install docs it requires JDK 17 (full JDK), Maven 3.8+, Ant 1.10+, PostgreSQL 14–17, **Apache Solr 9**, Tomcat 10.1, Node 20/22/24, PM2, manual SSL, and scheduled maintenance tasks — ten installation steps across two separately-deployed applications. No Lab stands up a Solr cluster. It is procured by an institution and run by IT, it produces an institutional repository and profile pages rather than _the Lab's own website_, and it expects data to arrive from institutional feeds rather than having anything like LabKit's ingestion engine at lab scale.
- **The positioning is two sentences for two audiences, not one sentence that fails at both.** The wedge claim, to PIs and Lab Editors, is mechanism-specific: **"Paste your ORCID. Get your lab's website."** — demo-able in thirty seconds, already substantially built, and unmatched at lab scale. The category claim, to research offices, JOSS reviewers, and eventual Western institutions, is **"a research information system small enough for one lab to run."** Nothing is oversold because the category claim lives in the _architecture_, not the marketing — the Lab experiences the wedge and never has to know it is using a CRIS. Trying to justify the category claim to Labs (who don't care) is why it kept feeling unearned; `VISION.md`'s "the website is the wedge, not the moat" was already this idea but, un-split, functioned as permission to keep building moat that no user could test.
- **The Bangladesh pilot pool cannot validate the compliance thesis at any sample size, and this is a seam in the go-to-market plan rather than a fatal flaw.** DIAL is a local partner onboarded for particular tasks, not the grant holder, so it carries no funder compliance burden; MI Lab and BRAC labs are structurally similar. What _does_ transfer to a Western pitch: the website/maintenance value prop, the ingestion engine proven against genuinely harder data (DOI-less regional venues, ACM/IEEE proceedings without ISSNs, non-Latin author names), OSS adoption count, the JOSS paper, and the Operator runbook. What does **not** transfer: compliance automation and institutional CRIS integration — both unvalidated and not confidently buildable without a Western design partner. Consequence: compliance cannot be the reason anything gets built in the next 12 months, because nothing built for it can be tested.
- **America standardized the _form_; Europe standardized the _model_ — and LabKit sits closer to the American shape.** The US has no CERIF equivalent. It has **SciENcv** (NCBI), which generates the federal **Common Forms** (Biosketch, Current & Pending Support) from ORCID and My Bibliography, and the **RPPR** annual progress report. SciENcv is now **mandatory**: NIH requires SciENcv-certified Common Forms for all applications _and RPPRs_ submitted on or after **25 January 2026**; NSF already accepts it. So the Western compliance pain is document generation for a researcher, not interchange between institutions — which is lab-scale work, and ORCID-anchored, which LabKit already ingests. Parked, not pursued, per ADR-0001.
- **The local compliance analog to investigate is IQAC / AQAR, and it is a conversation rather than a search.** Every Bangladeshi university has a UGC-mandated **Institutional Quality Assurance Cell**, which files an **Annual Quality Assurance Report** to the UGC with research output as a covered domain, feeding accreditation through the QAACB. Whether this creates a real reporting burden that lands on labs is unknown and was not resolved. The cheapest way to find out is to walk into BRAC's IQAC and ask what they collect from labs each year and how — an hour, zero code, and the highest-information action currently available on the compliance question.
- **Both dashboards get parked, and the Admin Kit specifically must not be deleted.** V1's dashboard for the Lab Editor is the **Payload admin panel** with collections grouped — which, corrected later the same day, was **already done** since commit `01b4aa8`: Research (Publications, Projects, Team, Grants, Awards, ResearchThemes), Reference Data (Venues, Organizations), Import (ImportRuns, ReviewItems), with the base-template collections deliberately left ungrouped. The session originally recorded this as missing work and filed a ticket for it; the "gap" was a false negative from a `grep` that never ran, because zsh aborts an entire command when any glob in it matches nothing. General lesson for verification greps: a zsh `no matches found` line means the command **did not execute**, not that the pattern was absent — quote globs or use `find -exec` when a path may not exist. The initial recommendation to delete `src/app/(dashboard)` was **wrong** and was reversed on evidence: although the upstream checkout survives outside the repo at `~/Developer/web/shadcn-admin` (751MB, own git repo), the in-repo copy is 147 files and genuinely diverged — `login/components/user-auth-form.tsx` posts to `/api/users/login` (real Payload auth wiring the checkout lacks), and zero occurrences of `required_error` confirm the zod v4 adaptation held, along with the react-day-picker v9, `z.coerce.date()`, tabler-icon-typing and pagination-`href` fixes and the `/dashboard` route-prefix rewrite. Deleting it would mean redoing all of that from a v3-era template. But it should not keep _routing_ either: `/dashboard/login` and the error pages return 200 and register/forgot-password are unwired stubs, which on a real Lab's production site is a support liability and 147 files of unaudited public surface. **Recommended (not yet done): `git mv "src/app/(dashboard)" "src/app/_dashboard-kit"`** — the same Next.js private-folder trick already used for `_dashboard-legacy`, so the repo tells one story: two parked dashboards, one live admin surface at `/admin`, reversible with a single `git mv`.

## 2026-07-05

- **The import-hydrate job's crash-recovery model is lease-lock + watchdog, because Payload's queue cannot resume a died job on its own.** A Codex branch review confirmed the original job design's checkpoint claim was false: it persisted the run doc only after a whole 20-item batch and queued its successor after that, so a worker dying mid-batch left no progress _and no queued job_ — and reading Payload 3.85's `runJobs` source confirmed a crashed job stays `processing: true` forever with `retries: 0` (never re-picked by cron), so recovery must come from a separately queued job. The rework (same commit as this entry): (1) the run doc is checkpointed after **every candidate** (statuses, progress recomputed from candidates, reportSummary); (2) ImportRuns gained a hidden `lock` group (`token`, `heartbeatAt`) claimed via the Mongo adapter's conditional `db.updateOne` — a real compare-and-swap (verified: `findOneAndUpdate` returns null on no-match), heartbeat refreshed on each checkpoint, stale lease (5 min) taken over — which is what actually enforces the spec's single-worker model rather than queue `limit` alone; (3) every invocation queues a `waitUntil`-delayed **watchdog** job before processing, and a claim-losing duplicate requeues itself with a delay instead of exiting, maintaining the invariant "a non-terminal run always has ≥1 queued job"; watchdogs no-op against terminal runs. `finalizeRun` is now idempotent (deletes the run's review items before recreating — safe because items can't have been human-resolved before the run finished) and releases the lease. Same review wave fixed: the zero-author guard firing only when `merged.length > 0` (true zero-author metadata hit `minRows: 1` and failed the run — now always a review item), staged-but-never-selected no-DOI/ambiguous candidates silently vanishing in the job path (now flagged at finalize; user-deselected DOI-bearing candidates stay silent — deselection is a decision, a staging warning note is not), person-merge suggestions now persisting structured `{newTeamId, existingTeamId, score}` in review-item `data` (paying off the Wave-1a "ids baked into display strings" debt; restoreReport round-trips them across batches), and `queueImportRun` as the sanctioned queue-first-then-mark-running kickoff (marking `running` before a failed queue call stranded runs unrecoverably — the parked legacy dashboard action still does this; the rebuilt dashboard must use the helper). All verified live against real MongoDB by `scripts/ingestion/verify-jobs-queue.ts` (kept as a repeatable regression check — 13 checks: contention, stale-lease takeover, mid-run checkpoint visibility, review-item kinds, watchdog no-op drain), which uses only DOI-less candidates so it never writes content collections. Note for future scripts: `payload run` exits after module evaluation without awaiting a floating `void main()` — use top-level `await main()`.
- **The "sidebar overlaps the page" bug was Tailwind v3 arbitrary-value syntax silently dying under v4, and labkit's `src/components/ui` had it in nine files.** `ui/sidebar.tsx` was the v3-era shadcn version using `w-[--sidebar-width]`; Tailwind v4 only treats the parenthesized form `w-(--sidebar-width)` as `var()` shorthand, so the class generated no CSS at all — the invisible spacer div that pushes page content sideways had zero width and the `fixed` sidebar painted over the page in both expanded and collapsed states. Fix: adopted the kit's v4-syntax `ui/sidebar.tsx` wholesale (exports are name-identical, so legacy `components/dashboard/*` importers still compile) and converted every remaining bare `[--var]` utility in `src/components/ui` to `(--var)` (calendar `--cell-size` sizing, chart legend swatch colors, dropdown/context/menubar/hover-card/popover/tooltip `origin-[--radix-*]` transform origins — all silently broken sitewide, not just in the dashboard). Verified by grepping the dev-server's compiled stylesheet for `width: var(--sidebar-width)`. General lesson: code vendored from pre-v4 shadcn templates compiles and lints clean while producing no CSS — grep for `-[--` when importing any older shadcn component.
- **The dashboard was rebased onto the shadcnblocks Admin Kit wholesale; the hand-built v1 dashboard is parked, not deleted.** The `shadcn-admin/` checkout (a separate nested git repo, excluded from labkit's `tsconfig.json`/ESLint) was copied in as the new `src/app/(dashboard)` route group — all template pages (dashboard-1/2/3, tasks, users, developers, full settings tree, auth, error pages) now live under `/dashboard/*`, with supporting components in `src/components/layout`, `src/components/errors`, ~17 root-level `src/components/*.tsx` files, `hooks/{use-toast,use-dialog-state}`, and `lib/{filter-countries,notify-submitted-values}`. The previous working dashboard (import wizard, review queue, runs, people, publications, LabInfo settings + their server actions) moved intact to `src/app/_dashboard-legacy/` — a Next.js private folder, so it stays compiled and importable but unrouted — to be ported into the template shell page by page. Rationale: the v1 dashboard had already borrowed the template's shell piecemeal; owning the whole kit gives every future feature a ready-made page pattern instead of re-deriving one per feature.
- **Template code was upgraded to labkit's dependency versions, never the reverse, and shared `src/components/ui` primitives were not overwritten.** Labkit runs zod v4, react-day-picker v9, @tabler/icons v3.44, RHF 7.80 — newer than the kit's. Copied code was adapted: `required_error:` → `error:`, Calendar `initialFocus` → `autoFocus`, `z.coerce.date()` → `z.date()` (zod v4 makes coerce input `unknown`, breaking `zodResolver` typing), tabler icon fields typed as `Icon` directly, and pagination controls got explicit `href="#"` because labkit's `PaginationLink` wraps Next `Link` (the kit's wrapped `<a>`). Only two ui files were added (`toast`, `toaster`) and one was extended in place (`scroll-area` gained the kit's optional `orientation` prop, default-vertical so frontend usage is unaffected). New deps: `@faker-js/faker`, `@radix-ui/react-icons`, `@radix-ui/react-toast`, `@radix-ui/react-visually-hidden`, `country-region-data`, `date-fns-tz`. `src/lib/utils.ts` is a one-line re-export of `cn` from `@/utils` so hundreds of copied `@/lib/utils` imports work unmodified.
- **Payload auth was ported as the first real feature: the template's login UI now actually authenticates.** `dashboard/(app)/layout.tsx` got the same `requireAdminUser()` guard (`getMeUser` + `checkRole(['admin'])` → redirect `/dashboard/login`) the legacy layout had, and `(auth)/login`'s `UserAuthForm` was rewired from the kit's fake `nofitySubmittedValues` submit to `POST /api/users/login` with the legacy page's error/forbidden handling (social-login buttons removed as dead UI; register/forgot-password remain unwired templates). Verified live: `/dashboard/login` 200, `/dashboard` and `/dashboard/settings` 307 → login, error pages 200; `tsc` and `lint` clean (8 pre-existing-pattern react-compiler warnings). Route links across all copied files were rewritten with a `/dashboard` prefix — note the first sed pass silently no-oped because zsh doesn't word-split unquoted `$VAR` (the re-run used `find -exec`), worth remembering for future bulk rewrites.
- **Citation-paste LLM assist is Gemini-gated, not Anthropic-gated, because the implementation must follow the current operator decision rather than an older draft plan.** `src/lib/ingestion/llm.ts` uses the current unified Google SDK (`@google/genai`) behind `process.env.GEMINI_API_KEY`, and `src/lib/ingestion/staging.ts` only swaps the _segmentation source of chunks_ for `stageCitationCandidates` when that key is present. Earlier planning notes had assumed Claude/Anthropic; that was explicitly overridden before implementation, so the code and `.env.example` now document Gemini instead. Scope stayed deliberately narrow: this LLM path is only for citation-text segmentation and best-effort field hints (`segmentCitations`, `extractCitationFields`), never for enrichment source-of-truth or any author/team identity decision.
- **The deterministic citation path remains the real safety net; Gemini is an opportunistic pre-processor, never a dependency.** `stageCitationCandidates` still runs the same per-chunk DOI extraction and `selected`/`note` logic it always did. The only change is how the chunk array is sourced. `src/lib/ingestion/llm.ts` is designed to fail closed: missing `GEMINI_API_KEY`, SDK/network errors, non-JSON responses, or Zod validation failures all silently fall back to the existing blank-line split behavior (`/\n{2,}/`), so operators without a Gemini key keep exact pre-feature behavior and operators with a key do not lose the deterministic path if the model path flakes.
- **LLM output is intentionally kept outside the people-matching boundary, and DOI-like strings are treated as untrusted unless they already exist in the raw input.** This follows the same safety split documented at the top of `src/lib/ingestion/people.ts`: person matching can change a real public-facing identity, so it remains deterministic-only (ORCID/DBLP exact, exact-name only, never fuzzy/LLM-assisted). The new Gemini helper is therefore not imported into `people.ts` or `match.ts`. Within `src/lib/ingestion/llm.ts`, any DOI-looking string emitted by the model is verified as an exact substring of the original source text before it is trusted; for segmentation, an invented/mangled DOI causes the whole LLM result to be discarded in favor of blank-line chunking, and `extractCitationFields` never exposes an LLM DOI at all.
- **"People" now means everyone in the publication graph, not just pre-vetted lab members.** `src/lib/ingestion/people.ts`'s `resolveOrCreateTeamMember` deliberately reverses this file's own 2026-07-03 "Team is never written by importers" position: on a safe-person-match miss, Publications ingestion now creates a real `team` record for every co-author instead of dropping them into `Publications.authors[].customAuthor` as a free-text holding pen. Reason: the holding-pen version pushed the identity/data-entry work back onto the operator, which is exactly the toil the ingestion product was supposed to eliminate. The safety split is **unchanged**: ORCID/DBLP-exact and exact-name-only remain the only auto-link tiers; fuzzy people-name matches are still never auto-applied to an existing Team row, only surfaced as `report.suggestDedupe` / `review-items` merge suggestions for a human to confirm later. The crucial public-site safety invariant is now centralized in one unconditional `data` object reused by both the `upsertByKey(...)` path and the plain `payload.create(...)` fallback in `resolveOrCreateTeamMember`: every importer-created person gets `source: 'import'` and `displayInWebsite: false`, making "is in the publication graph" and "is shown on the website" two intentionally separate decisions.
- **`import-runs` and `review-items` are now first-class persistence, even for dry-runs, because they serve different lifecycles.** `src/collections/ImportRuns/index.ts` is immutable run history (`params`, staged `candidates`, `progress`, final `reportSummary`); `src/collections/ReviewItems/index.ts` is a mutable work queue (`status`, `resolution`) that operators work down over time. The engine shape in `src/lib/ingestion/staging.ts` and `src/lib/ingestion/run-persistence.ts` is now explicitly two-phase: staging fetches/parses only (`stageOrcidCandidates`, `stageBibtexCandidates`, `stageCitationCandidates`) and does **no** Crossref/OpenAlex hydration or DB writes; hydration/persistence happens afterward, with `persistRunProgress` and `finalizeRun` writing the bookkeeping regardless of `dryRun`. That `dryRun` gate is intentionally narrower: only the real content collections (`publications`, `team`, `venues`, `organizations`) no-op their writes, while runs/history/review-queue still persist so CLI dry-runs and the future dashboard both have an auditable record of what happened and what still needs human review.

## 2026-07-03 (even later)

- **DBLP added as a third structural author-matching tier**, alongside ORCID and exact-name in `matchPersonToTeam`/`dedupeCustomAuthor` (`src/lib/ingestion/people.ts`). Unlike ORCID (sparse in practice — see this doc's earlier entry) DBLP publication records embed already-disambiguated author `pid`s per paper, so it's structural third-party evidence, not a name-similarity guess — safe to rank alongside ORCID, above exact-name, still nowhere near the banned fuzzy tier for people. `Team.dblp_pid` is manual-entry only (mirrors `orcid`/`openalex_id` exactly) — never auto-searched-and-assigned, which would reintroduce the homonym risk this design avoids.
- **Resolution is title+year search (`dblp.org/search/publ/api?format=json`), not a DOI endpoint** — DBLP has no confirmed direct DOI lookup. Verified live against a real CHI 2026 DOI before writing `src/lib/ingestion/dblp.ts`: the search JSON embeds `info.authors.author[].{@pid,text}` inline, so no XML-parsing fallback or new dependency was needed after all (the plan's contingency for this went unused). One real quirk confirmed live: DBLP's XML-to-JSON conversion collapses a single-item list (`hits.hit`, `authors.author`) to a bare object instead of a one-element array — handled with a small `asArray()` normalizer, same defensive-shape pattern as `normalizeIssn` from the prior entry.
- **DBLP enrichment is additive and silent-on-miss, not a hard requirement.** DBLP only covers ACM/IEEE/CS venues (not JMIR-type medical-informatics venues also in DIAL's corpus), so `hydratePublicationFromDoi` never calls `flagUnmatched` when DBLP has no record — only Crossref+OpenAlex both missing is treated as a hard failure, same as before this change.
- **Author-list alignment between DBLP and Crossref/OpenAlex uses name-similarity matching (`attachDblpPids`), not array position** — unlike `mergeAuthors`' Crossref/OpenAlex merge (which reuses position since both APIs preserve submission order), DBLP's own author count/formatting can differ slightly (e.g. accented names, middle-initial handling), confirmed live: DBLP rendered "Dragan Ahmetović" without the accent, but dice-coefficient similarity against the normalized name still matched all 4 authors on a real CHI 2026 paper correctly on first live test.
